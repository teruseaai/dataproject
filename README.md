## 3. 고른 해결 방법

| 기능 | 고른 해결 |
|---|---|
| 다른 사람의 변경 보기 | 쉬운 해결(새로 고침 단추) |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운 해결(지원 단계에서 필수 포함 역할을 채울 자리가 모자라게 되는 지원을 막음) |
| 같은 팀에 대기 중인 지원이 여럿 | 어려운 해결(승인 직전에 규칙을 다시 검사함. 마지막 찬성이 들어온 순서대로 처리됨) |
| 마지막 자리에 두 명이 동시에 들어감 | DB의 유일성 제약을 둠(schema.sql). 충돌했을 때의 화면 안내는 만들지 않음 |
| AI 응답이 늦을 때 | 어려운 해결(요청을 별도 작업으로 돌리고 모델마다 120초 전체 대기 시간을 재서 끊음). 가짜 모델로만 시험함 |
| 3차 모델까지 실패 | 어려운 해결(모든 경우를 따져 다섯 가지 검사를 통과하는 배정을 찾음) |
| AI 대기 중 화면 | 어려운 해결(몇 차 모델의 응답을 기다리는 중인지 보여 줌) |
| DB 일시정지 막기 | 쉬운 해결(마감 날 배포한 앱을 써서 DB 요청을 만듦) |

## 5. 오픈라우터 AI 모델 호출 실패 사례

쉬움 시나리오의 6단계(AI 배정)에서 세 모델이 모두 실패했고, 앱이 걸러 내고 스스로 배정했습니다.

- 1차 모델은 배정안을 JSON으로 읽을 수 없는 답을 내서 앱의 검사에 걸려 2차 모델로 넘어갔습니다.
- 2차 모델은 `RuntimeError`로 실패했습니다. 이 오류는 앱이 빈 응답일 때 내도록 만든 것입니다.
- 3차 모델(당시 thinkingmachines/inkling:free)은 `HTTPError`로 실패했습니다. 이후 같은 모델을 직접 불러 보니 403이 나왔고, 에이전트 도구 안에서만 쓸 수 있는 모델이라는 메시지였습니다. 그래서 cohere/north-mini-code:free로 바꿨습니다.
- 세 모델이 모두 실패하자 앱이 스스로 규칙을 지키는 배정을 만들었습니다.

## 6. 클로드가 잘못된 추론이나 답변을 한 사례

클로드가 처음 만든 DB 연결 코드(db.py)가 Supabase의 연결 방식과 맞지 않았습니다.

- 일어난 일: 명단으로 처음 상태를 만드는 시험(service.py의 start_scenario)을 같은 명령으로 두 번 실행했을 때 `psycopg.errors.DuplicatePreparedStatement: prepared statement "_pg3_0" already exists` 오류가 났습니다.
- 클로드의 설명: 같은 SQL을 여러 번 보내면 psycopg가 준비된 명령을 자동으로 만드는데, Supabase의 연결 중계 장치와 충돌한다고 했습니다. 이 설명을 따로 검증하지는 않았고, 고친 뒤 같은 시험이 두 번 모두 통과하는 것을 확인했습니다.
- 알아챈 방법: 같은 시험 명령을 한 번 더 실행했을 때 나온 오류 화면입니다.
- 고친 곳: db.py의 연결 만드는 줄에 `prepare_threshold=None`을 더했습니다. 이 줄은 커밋 b8c68cd의 db.py에 들어 있습니다. 이 커밋은 고친 뒤 처음 저장한 것이라, 고치기 전의 코드는 커밋 기록에 남아 있지 않습니다.
## 7. 제출한 앱에서 발견한 문제점과 개선할 점

제출한 앱에서 발견한 문제가 두 가지 있습니다.

**1. 배포한 앱이 어떤 코드로 돌고 있는지 알 수 없음 (어려움 시나리오 11단계)**

- 문제: 어려움 시나리오 11단계(학생14가 팀3에 지원)에서 `막힘: 필수 포함 역할을 맡을 학생의 자리가 모자람`이 나와야 하는데, 처음에는 막히지 않고 지원이 접수되었습니다. 앱을 Reboot app으로 다시 시작하자 기대대로 막혔습니다.
- 원인: 확인하지 못했습니다. 푸시한 새 코드가 아직 반영되지 않은 상태였을 가능성이 있지만, 그 장면에서 팀3의 구성을 확인하지 않아 단정할 수 없습니다. 이 장면의 화면은 남기지 못했습니다.
- 개선할 점: 화면에 코드 버전(커밋 번호)을 표시하면 배포한 앱이 새 코드로 돌고 있는지 바로 알 수 있습니다. 만들지 못했습니다.

**2. DB 연결 하나를 모든 접속이 공유함 (관리자 화면 시험 중)**

- 문제: 관리자 화면을 시험하던 중 팀 목록을 그리는 곳에서 `psycopg.errors.InFailedSqlTransaction: current transaction is aborted, commands ignored until end of transaction block` 오류가 났습니다. 앱을 다시 시작하면 정상이었습니다.
- 원인: 처음 실패한 DB 명령을 찾지 못했습니다. 연결을 하나만 만들어 계속 쓰는 구조라서, 한 번 실패한 상태가 앱이 켜져 있는 동안 계속 이어졌습니다.
- 조치: 연결이 실패한 상태이면 되돌려서 다시 쓰게 하는 코드를 db.py에 더했습니다(커밋 95dc9da). 원인을 없앤 것이 아니라, 같은 일이 생겨도 앱이 계속 돌아가게 한 안전장치입니다.
- 개선할 점: 원인이 되는 명령을 찾아야 하고, 접속마다 따로 연결을 쓰는 구조도 검토해야 합니다.
